# Codex review of Kiro M1 requirements — 001

Before design/implementation approval, correct these concrete issues in the initial requirements draft:

1. No digest self-reference. Compute the basis hash over a documented material-state projection excluding the digest field itself, logs and unbounded history. SHA-256 is collision resistant; do not promise distinct hashes for EVERY different input as an absolute theorem.
2. Preserve uncertain provider outcomes. An absent adapter is unconfigured. An adapter exception/timeout is an error or unknown, never reclassified as unconfigured. No synthetic success or automatic retry. M1 does not invoke a live adapter.
3. Hosted response shapes: the engine uses outcome, selected_candidate_id, trace.lambda_decisions (an ordered array of exactly 12 gate records), receipt and false authority flags under docs/EVALUATE-INTEGRATION.md. A product-level status union may wrap that transport, but must not replace or misname the actual protocol. A refusal also has a receipt. Prefer future typed seam rather than an invented partial API.
4. Kiro 3.4.0 hooks: current official docs CONFIRM that version v1 plus a hooks array with PostFileSave and a path matcher is valid in CLI V3 (https://kiro.dev/docs/hooks/ and https://kiro.dev/docs/hooks/types/). The initial concern about PostFileSave was resolved by checking those docs. PostToolUse is also available. Hook activation and a manually run check are separate observations. Add the hook after build scripts exist, then observe it firing in a Kiro session.
5. A rejected attempt may append an audit event or consume its action ID, but must preserve the simulated operational state, tick and revision. State this consistently with append-only history. Successful replay should return a duplicate/rejection outcome and never reapply effects. Define proposal confirmation explicitly and reject mismatched payloads sharing an action ID.
6. Units and temporal causality: define tick seconds, request arrival/service rates, worker/DB connection units, and how observations differ from predictions. Stopping by tick limit is not a recovery success. Test both outcomes.
7. Local toolchain: Node v22.23.2. The existing global npm launcher is broken. Use node /private/tmp/blackout-toolchain/package/bin/npm-cli.js for local installs/scripts, or PATH=/private/tmp/blackout-toolchain/package/bin:$PATH scoped to the command. npm 10.9.2 was downloaded from registry.npmjs.org with SHA-512 integrity checked. Leave global toolchain untouched. Project-local dependency installation is allowed; no paid/hosted operations.

The first CLI milestone proves invariants. The final product target remains a full incident recovery experience with actual hosted Evaluate, not a CLI-only entry. Draft specs and passing local tests do not establish hosted behavior, usability results, or a completed submission.
