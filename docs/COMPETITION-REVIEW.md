# Kiroween 2026 review

Reviewed 2026-11-16 Pacific. Canonical sources: [Official Rules](https://kiroween.devpost.com/rules), [Overview](https://kiroween.devpost.com/), [Resources](https://kiroween.devpost.com/resources).

## Entry gates
New application built during October 30–December 4, 2026. Deadline December 4 at 2 PM Pacific; no extension. Substantial Kiro use is mandatory. Existing tools/APIs may be incorporated with disclosure and permission. Solo entry is allowed; teams have at most three people. Founder eligibility still needs confirmation when registering.

Submit a working app URL, public GitHub repository with an open-source license and tracked root .kiro directory, a Kiro usage write-up, and a public YouTube demo under three minutes. Preserve judge access through January 29, 2027 at 1 PM Pacific. Repo stays private until a reviewed public release.

Five equally weighted criteria: Impact, Implementation, Design, Innovation and Presentation (20% each). Implementation specifically scores effective Kiro use. A working application and clear end-to-end demonstration are essential.

Target Frankenstein category. Overall awards: $30,000/$20,000/$10,000; category award $5,000; startup bonus $10,000 subject to eligibility. One overall OR category award plus eligible bonuses. Eligible entrants can request 4,000 Kiro credits by December 1 noon Pacific; redemption deadline December 4, redeemed expiry December 31.

## Project response to the rules
- Entire app begins in a fresh repository during the eligible window. Hosted Evaluate is disclosed as pre-existing technology.
- Build records must show Kiro creating/revising requirements, design, implementation, tests and hooks. A decorative .kiro folder does not establish usage.
- Frankenstein fit: combine a deterministic service model, agent proposals, hosted bounded evaluation and evidence-bound execution into one incident recovery experience.
- Initial work is local and unpaid. Live API use, hosting and public disclosure each need the concrete plan and applicable authority.
- Public release must include all application code and a documented external Evaluate integration. Document that external dependency, access requirements and reproducibility limits in the release review before submission.
