# Disposable measured process rig — implementation requirements

Purpose: supplement the deterministic teaching model with a real, reproducible incident experiment. Never relabel simulated ticks as measured production telemetry.

Implement project-owned Node child worker processes (known compiled module only), an actual loopback HTTP ingestion endpoint and a durable local queue. Jobs contain only fixed-size fictional workload; no user code, shell, URLs, file paths or credentials. Parent records admitted/rejected/completed/failed counts and wall-clock timestamps. Workers perform a bounded real computation and acknowledge job IDs. Persist queued/completed records with node:sqlite or a synchronized append log; demonstrate restart recovery of pending jobs in a disposable test directory. Record actual PID/start/exit status and cleanup. Do not call a provider or open a public port.

Hard bounds: at most one rig globally, four workers,64 jobs/run,30 seconds lifetime,1MiB stored evidence; loopback ephemeral port. Caller can select only named presets and allowlisted effects. No arbitrary parameters, process paths or commands. Always stop child processes, close sockets and remove test-only temporary artifacts; retain sanitized evidence bundles. If a child response is uncertain, record unknown and stop rather than dispatching its job again blindly.

Expose a small driver interface: observe -> propose bounded remedies from real counters -> exact basis/payload hash -> human confirms named lab action -> apply once -> observe actual throughput/backlog. A worker-stop injection must change the revision/digest. A confirmation staged before it must fail current-basis validation. Named effects: resume a lab worker, add one worker within cap, cap ingestion. The UI must say which observations are measured process counts and which are deterministic predictions. If this measured workflow is a secondary surface, keep it clearly separate from model ticks and exported evidence.

Testing: actual worker process starts, consumes fixed job, stops and recovers; queue durability; stale action no effect; duplicate action once; concurrency and ownership; forced timeout cleans up; fixed caps. No benchmark claiming general production performance. Comparison uses same workload and injected event schedule, identical execution guards, reports actual source/environment and includes a no-action/control baseline. Do not credit Evaluate for improvements introduced by local filtering or human choice; isolate the selector for that claim or explicitly decline it.

M4 also includes read-only MCP observations used by a real Kiro session and evidence of a functioning hook, with actual native tool/session records. No credit for configuration alone.

## Concrete measured scenario to keep the first run reliable

Use one initially paused real worker and64 fixed fictional jobs admitted over loopback HTTP. A paused queue is stable during human review; do not continuously mutate the basis while asking for approval. Use node:sqlite for a durable parent-owned queue. A worker performs a bounded hash computation and SELECT1 on a managed SQLite handle, then acknowledges its exact assigned job ID. Parent commits completion. Pending rows survive restart; inflight rows after uncertain termination become unknown and must not be blindly re-executed.

The measured lab declares its own100-handle DB budget. Track actual opened SQLite handles (not production PostgreSQL telemetry), including deliberately reserved parent handles and3 per worker. Initial total48 with1 worker; proposed scale to4 projects57/100. A named pressure injection reserves extra lab handles to94; adding3 workers now projects103/100 and is rejected. Existing paused worker may still be resumed without new handles. This is an explicit lab resource policy, not a benchmark of SQLite's actual maximum or production database pressure. Evidence labels must say managed SQLite handles.

Named remedies: analyze adding3 workers (up to4), analyze resuming the existing paused worker, compare ingestion cap. These are review activities; chosen option maps to a distinct human-confirmed managed action. Bind observation, exact action parameters, handle ownership, pool state and queue counts to the rig's revision/digest. Pressure must invalidate a previously staged action. Fresh scale fails projected resource limit; fresh resume can drain jobs. After apply, measured completed/backlog counters change and history records timestamps. Server reads actual counters at the final gate. Unknown outcomes never authorize another effect.

A lifecycle limit of120 seconds (replacing30 for interactive review) bounds each rig; actual work remains64 jobs and four workers max. No continuous CPU while paused. One rig globally, session-owned; reset/disconnect/expiry/shutdown closes sockets, SQLite handles and children, always resumes a stopped child before termination if OS signals are used. Prefer IPC-controlled pausing before dispatch, no platform-specific SIGSTOP required. Lifecycle tests use shorter injected deadlines. No real network destinations or arbitrary code.

Implementation reference: Node22 official node:sqlite API https://nodejs.org/docs/latest-v22.x/api/sqlite.html. The installed Node is22.23.2; inspect built-in module availability before implementing and keep any experimental warning explicit. Use the existing @types/node22 dependency and no third-party database/server installer. Kiro MCP configuration reference is https://kiro.dev/docs/mcp/configuration/. Read-only observability tools must expose bounded fictional run data, not credential access, filesystem traversal or actuation. Protocol-test any MCP endpoint through an actual client; Kiro's exhausted quota means configuration alone cannot be claimed as observed Kiro tool use.
